# 发布完整性

当部署的工件是仓库证明的工件、操作仅使用其需要的权限、并且运行结果经过验证时，发布是可信的。

## 构建一次

源代码格式化、生成和静态检查应用于为发布选定的确切源状态。CI 然后从固定的、可审查的输入中产生一个不可变的工件，并附加标识其来源和构建的来源证明。工件级测试、安全检查和浏览器证明在声明依赖于编译或打包的地方锻炼产生的工件。

部署作业应在没有源代码签出、开发工具链或包注册表的最小环境中消费该工件。特权重建会产生第二个未经证明的工件，并扩大关键供应链。

## 限制发布权限

使用能完成操作的最小工作流权限和凭据生命周期。将评估和准备与生产切换分开。worker 应请求针对命名资源的命名操作，而无需接收授权它的凭据。一个受信任的代理可以在执行时从安全存储中解析密钥，将其保存在代理内存中，仅注入或应用于该操作，并返回操作的收据和观察到的后条件。Ryan 的 [`gh` sidecar example] 将 GitHub CLI 流量路由通过一个持有密钥材料的代理，使 `gh` 对 agent 来说仍然是一个普通工具，同时 token 留在模型可读的 context 和仓库之外。

[`gh` sidecar example]: https://x.com/_lopopolo/status/2061150109232939288

重要的更改应暴露显式阶段：

1. 检查当前状态；
2. 准备候选工件和回滚材料；
3. 部署到隔离的金丝雀；
4. 验证真实的健康和访问路径；
5. 获得所需的审批；
6. 切换；
7. 验证生产环境；以及
8. 保留或执行回滚。

agent 可以拥有每个可逆阶段，而人类保留批准重要转换的权限。

[authority thesis] 阐述了身份、密钥隔离、最小权限、审批和撤销跨所有 agent 操作。

[authority thesis]: ../authority/

## 证明部署的边界

上传或成功的工作流不是用户结果。检查托管基础路径、服务健康、关键浏览器或 API 旅程，以及操作可能破坏的任何访问路径。记录简洁的证据和足够的状态来诊断或逆转故障。

当金丝雀与生产环境锻炼相同的二进制文件、身份形状、网络和健康检查，同时限制影响时，它们是有用的。仅测试安装但不可达的金丝雀不能证明远程升级是安全的。
